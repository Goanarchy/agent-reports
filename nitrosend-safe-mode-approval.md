- **Step that slowed the run most.** Turning Safe Mode on. `PATCH /v1/my/account` with `Authorization: Bearer nskey_live_â€¦` returns HTTP 403 `{"code":403,"message":"Not authorized","error":true}`; the identical body sent with the JWT from `POST /v1/login` returns 200. The documented setup lists the PATCH call without saying which credential class can perform it.
- **Doc gap, with repro: the decision endpoint refuses the API key, and the error does not say so.** Repro: `PATCH /v1/my/account` with `{"safe_mode_enabled":true}` and an API-key bearer â†’ 403 `Not authorized`; repeat with the logged-in JWT â†’ 200. The same split exists on the decision call: `POST /v1/my/map/approvals/508` with `{"decision":"approve","version":"sha-256:â€¦"}` needs the sign-in credential, and an API key gets 403 even though the tool surface lets an API-key agent create the campaign being decided.
- **Doc gap, with repro: the review URL in the email differs from the documented path.** The approval email's `human.url` is `https://app.nitrosend.com/approve/508?account_id=13745&brand_id=13930`, while the account docs describe the review page as `/my/map/reviews/<id>`; the machine path is `/v1/my/map/approvals/508`. Three different shapes for one object. Also, `GET /v1/my/map/approvals/508` returns the campaign HTML but not the MAP 0.3 description, so a connector that wants to validate before deciding has to parse the MIME part out of the email.
- **One change I would make.** Return the MAP 0.3 description as a `mail_action` object on `GET /v1/my/map/approvals/{id}` (the same bytes as the `application/ld+json; profile="https://mailschema.org/profiles/map/0.3"` part), so a MAP connector can validate and decide against the same object without re-parsing email, and make the 403 from `PATCH /v1/my/account` name the required credential class instead of `Not authorized`.
